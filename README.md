# Редакторская редИИска — самостоятельный пилот

Подготовленная версия редакторской платформы без зависимости от Sites и аккаунтов ChatGPT.
Стек: Cloudflare Workers (сервер), D1 (SQLite), Cloudflare Access (вход по коду на почту), обычный HTML/JS.
ИИ не подключён. Запуск в чужом аккаунте в рамках подготовки не выполнялся.

## Что сохранено

Проекты, роли шеф/редактор/внешний сотрудник, брифы и вопросы, текстовые поля с лимитами,
ручное ревью, история версий, база правил и примеров с утверждением, экспорт.
Внешние сотрудники видят только назначенные задачи своих проектов и разрешённые утверждённые знания.
HTML, примеры и API закрыты проверкой подписи Cloudflare Access и членства в редакции.
Email-заголовки без подписанного токена не принимаются. Пустая настройка входа закрывает приложение.

## Стоимость и доступность

Выбирать только бесплатные Workers, D1 и Zero Trust Free. Не включать платные планы/автопокупки.
Cloudflare Access Free рассчитан на команды до 50 пользователей; Workers Free — до 100 000 запросов в сутки,
но также есть лимиты процессорного времени и операций D1. Это пилот, а не обещание неограниченного сервиса.
При достижении бесплатных квот возможны ошибки. Следить за Usage в панели.
Cloudflare сообщает о проблемах доступа у российских провайдеров. Сначала проверить вход
и загрузку интерфейса у двух участников из их обычных сетей. Если не работает — не переносить рабочие материалы.

Официальные источники:
- https://www.cloudflare.com/plans/developer-platform/
- https://www.cloudflare.com/plans/zero-trust-services/
- https://developers.cloudflare.com/d1/platform/pricing/
- https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/

## Запуск владельцем: подготовка

Нужны бесплатный аккаунт Cloudflare, GitHub и Node.js 22.13+.
Аккаунт Cloudflare нужен владельцу; сотрудникам нужен только доступ к почте.

1. Создать **приватный** репозиторий GitHub `rediiska` и загрузить содержимое папки.
   Не загружать node_modules, .wrangler, секреты или резервные копии данных.
2. На компьютере открыть терминал в папке, выполнить:

```sh
npm ci
npx wrangler login
npx wrangler d1 create rediiska-db
```

3. Из ответа последней команды скопировать database_id в `wrangler.jsonc`, заменив
   `REPLACE_WITH_YOUR_D1_DATABASE_ID`. В `vars.OWNER_EMAIL` указать свою почту,
   на которую будет приходить код входа. Пустой OWNER_EMAIL не даёт создать редакцию.
4. Создать таблицы и опубликовать сервер (до настройки Access он будет отвечать отказом):

```sh
npm run db:migrate
npm run deploy
```

Команда выдаст реальный адрес вида `https://rediiska.<ваш-поддомен>.workers.dev`.
Этот адрес не создан автоматически при подготовке архива.

## Настроить вход

1. В Cloudflare Zero Trust выбрать Free, задать team name и включить способ входа One-time PIN.
2. В Workers & Pages открыть Worker `rediiska`, включить Cloudflare Access для его адреса
   workers.dev / всего Worker. Интерфейс панели может называть это Access либо Domains & Routes.
   Защитить весь адрес, включая /api/* и файлы. Не создавать Bypass/Everyone.
3. В политике Allow указать **конкретные email** — сначала только владельца.
4. Из настроек приложения Access скопировать Application Audience (AUD).
   В `wrangler.jsonc` заполнить `ACCESS_AUD` и `ACCESS_TEAM_DOMAIN`.
   Последний имеет вид `https://<team-name>.cloudflareaccess.com`, без пути.
5. Повторить `npm run deploy`.
6. Открыть реальный адрес в браузере. Ввести разрешённую почту, получить код,
   войти. Владельцу будут созданы пять стартовых проектов. Удалённых производственных данных здесь нет.

Документация:
- https://developers.cloudflare.com/workers/configuration/cloudflare-access/
- https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/

## Добавить коллегу

1. Разрешить email в политике Cloudflare Access.
2. В редИИске открыть «Команда и доступы», добавить тот же email, роль, проекты.
3. Передать ссылку самостоятельно. Приложение приглашения не рассылает.
4. Для внешнего сотрудника назначить на его email конкретную задачу.
5. Проверить с ним: задача доступна, чужие задачи и внутренние правила не видны.

Участники не получают доступа к панели Cloudflare или репозиторию GitHub.

## Проверка перед пилотом

```sh
npm run check
npm test
npm run build
```

При подготовке пройдены TypeScript, серверные сценарии на SQLite, криптографические тесты
входа и сборка Wrangler без публикации. Тесты интерфейса используют имитацию DOM,
не настоящий браузер. Реальную почтовую доставку, вход, деплой и доступ из сетей участников
нужно проверить после настройки аккаунта.

## Данные и резервные копии

В архиве **код, схема и примеры**, а не копия рабочей базы из Sites. Сайт Sites продолжает
работать отдельно. Автоматической синхронизации между ними нет.
Первый запуск создаёт новую пустую редакцию со стартовыми проектами.
Не обещать перенос существующей истории через экспорт отдельных задач: он не равен полной базе.
Если в Sites уже есть ценные данные, нужен отдельный перенос полной базы с проверкой числа записей
и переназначением workspace/owner, поскольку система идентификации меняется.

Полная резервная копия новой базы:

```sh
npm run db:export
```

Полученный rediiska-backup.sql хранить приватно, не коммитить. Перед будущим переносом
во внутреннюю инфраструктуру сохранить все таблицы, включая task_versions и knowledge_versions.
D1 использует SQLite, не PostgreSQL. Переезд на PostgreSQL потребует адаптации SQL и импорта.

## Обновления через GitHub

Можно подключить приватный репозиторий к Workers Builds в панели Cloudflare.
Для существующего Worker выбрать репозиторий, задать команду развёртывания `npm run deploy`.
Убедиться, что используется та же D1 и те же переменные, а не новая пустая база.
Секреты хранить в настройках Worker, не в GitHub-коде.
Изменения схемы требуют отдельного запуска миграций; перед ними сделать резервную копию.

## API модели позже

Будущий запрос идёт из браузера в сервер редИИски, затем в модель. Ключ только на сервере.
В этой версии нет вызовов модели и нет формы для ключа. Понадобятся документация API,
модель, ограничения, адрес и доступность из Cloudflare. Если модель только внутри корпоративной
сети, потребуется согласованный шлюз или перенос сервера. Участники ключ не получают.

- lib/identity.ts — проверка подписанного входа
- lib/editorial/access.ts — права и привязка пользователей
- src/worker.ts — HTTP-маршруты и защита файлов
- drizzle/ — миграции SQLite/D1
- tests/ — серверные, авторизационные и интерфейсные проверки
